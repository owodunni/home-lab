Unified Identity Architecture for Kubernetes Home-Lab Environments: A Comprehensive Implementation Guide for Authentik Integration1. Introduction: The Strategic Imperative of Centralized Identity in Distributed SystemsIn the contemporary landscape of self-hosted infrastructure and home-lab environments, the shift from monolithic servers to distributed, containerized microservices orchestrated by Kubernetes has revolutionized deployment velocity and resource efficiency. However, this architectural decoupling introduces a significant fragmentation of security domains. A typical home-lab operating a suite of applications—ranging from media aggregation tools like Sonarr and Radarr to critical observability platforms like Prometheus and Grafana—often defaults to a disjointed security posture where each service manages its own authentication credentials, session lifecycles, and access control lists. This fragmentation not only imposes a substantial administrative burden, necessitating the management of disparate user accounts across a dozen distinct interfaces, but also expands the attack surface. A vulnerability in the authentication logic of a single peripheral application, such as a torrent client or a backup utility, can serve as a beachhead for lateral movement within the cluster.To mitigate these risks and elevate the operational maturity of the home-lab to enterprise standards, the implementation of a centralized Identity Provider (IdP) is paramount. This report articulates a rigorous architectural blueprint for deploying Authentik as a unified identity layer within a Kubernetes cluster. We will explore the integration of Authentik with the NGINX Ingress Controller to secure a specific target portfolio of applications: Backrest, Headlamp, Homepage, Jellyfin, Jellyseerr, Kube-Prometheus-Stack, Prowlarr, qBittorrent, Radarr, and Sonarr.Our analysis extends beyond mere configuration snippets. We will dissect the theoretical underpinnings of the two primary integration patterns—OpenID Connect (OIDC) and Proxy Provider Forward Authentication—evaluating their suitability for each application based on native capabilities, protocol adherence, and user experience requirements. Furthermore, we will address the complexities of "GitOps" style management, ensuring that configuration methodologies align with the declarative nature of Kubernetes, as implied by the reference to repository-based deployment structures. By the conclusion of this document, the reader will possess a holistic understanding of how to architect a Zero Trust environment where identity is verified at the ingress edge, session state is globally managed, and authorization policies are granularly enforced across the entire application stack.2. Architectural Foundations: Authentik in the Kubernetes Ecosystem2.1 The Split-Plane Architecture of AuthentikUnderstanding the successful deployment of Authentik in a Kubernetes environment requires a deep appreciation of its split-plane architecture, which divides responsibilities between the Control Plane (Core) and the Data Plane (Outpost). This separation is not merely an implementation detail but a critical design feature that impacts high availability, latency, and failure modes.The Authentik Core serves as the administrative heart of the system. It hosts the API server, the administrative dashboard, and the policy engine's configuration interface. It is responsible for persisting state into the PostgreSQL database and managing ephemeral session data in Redis. However, in a high-traffic Kubernetes cluster, routing every single authentication request through the Core would introduce a single point of failure and significant latency bottlenecks. If the Core were to go down during an upgrade or database backup, access to all protected applications would theoretically cease.To solve this, Authentik utilizes Outposts. The Outpost is the Data Plane component; it is a lightweight proxy or LDAP server that sits in the traffic path. In the context of Kubernetes, the Outpost is typically deployed as a standalone Pod (or set of Pods) that communicates with the Ingress Controller. The Outpost synchronizes configuration and policy data from the Core but executes the actual authentication decisions locally. This means that even if the Authentik Core is temporarily unreachable, the Outpost can often continue to validate existing sessions and enforce cached policies, providing a degree of resilience essential for maintaining access to critical infrastructure tools like Headlamp or monitoring dashboards like Grafana during maintenance windows.For the specific applications listed in this report, we will leverage the Proxy Outpost. This component is designed to interface seamlessly with reverse proxies like NGINX and Traefik. It supports two modes of operation that are pivotal to our deployment strategy:Forward Authentication: The Outpost acts as a decision engine. The Ingress Controller pauses an incoming request, sends a sub-request to the Outpost asking "Is this user authorized?", and based on the HTTP 2xx or 401 response, either forwards the traffic to the application or redirects the user to the login flow.OAuth/OIDC Provider: The Outpost (or the Core itself, depending on configuration) acts as the Identity Provider, handling the token exchange flows (Authorization Code, Implicit, etc.) required by applications with native SSO support like Grafana and Jellyfin.2.2 Ingress-Nginx and the Forward Auth PatternThe majority of the applications in the target suite—specifically the \*Arr stack (Sonarr, Radarr, Prowlarr), qBittorrent, and Backrest—were designed primarily for standalone operation and lack sophisticated native support for modern authentication protocols like SAML or OIDC. For these "legacy" or "simplified" applications, the Forward Authentication pattern is the industry standard for securing them in a cloud-native environment.The mechanism relies on the auth_request module within NGINX. When a user attempts to access https://sonarr.lab.local, the Ingress Controller triggers an internal sub-request to the Authentik Outpost service. This internal traffic remains within the Kubernetes cluster network, ensuring low latency. The Outpost evaluates the user's session cookie.Scenario A (Unauthenticated): The Outpost returns an HTTP 401 Unauthorized. NGINX intercepts this and redirects the user's browser to the Authentik login portal, appending the original requested URL as a query parameter (?rd=...) to facilitate a seamless return after login.Scenario B (Authenticated): The Outpost returns an HTTP 200 OK. Crucially, it also injects HTTP headers into the response, such as X-Authentik-Username, X-Authentik-Groups, and X-Authentik-Email. NGINX then strips these headers from the response to the user but adds them to the upstream request sent to the Sonarr pod. This allows the backend application, if configured to look for them, to identify the user without ever seeing a login form.This pattern essentially "wraps" the insecure application in a hardened security shell. The application itself can often be configured to disable its internal authentication entirely, trusting that any request reaching it has already been vetted by the Ingress/Authentik layer. This delegation of trust is the cornerstone of the Zero Trust model within the cluster: we trust the network path because we control the ingress points.2.3 The OIDC Standard for Modern ObservabilityIn contrast to the Forward Auth pattern, applications like Grafana, Jellyfin, and Headlamp support OpenID Connect (OIDC). This is a robust authentication layer built on top of OAuth 2.0. In this model, the application itself is "identity-aware."When a user accesses Grafana, the application detects the lack of a session and redirects the browser to Authentik (the Identity Provider). The user authenticates with Authentik, which then issues an ID Token (a JWT containing user claims) and an Access Token. Grafana receives these tokens and validates the cryptographic signature against Authentik's public keys.The strategic advantage of OIDC over Forward Auth for these capable applications lies in Authorization (RBAC). While Forward Auth can pass simple group names in headers, OIDC allows for complex claim mapping. We can configure Authentik to send a list of groups (e.g., "Grafana Admins", "Grafana Viewers") in the ID Token. Grafana can then parse this token and map "Grafana Admins" to its internal "Admin" role and "Grafana Viewers" to the "Viewer" role. This automates privilege management: adding a user to a group in Authentik instantly grants them the correct permissions in Grafana without manual intervention in the Grafana database. This capability is critical for the Kube-Prometheus-Stack, where distinguishing between users who can edit dashboards and those who can only view them is a common requirement.3. Deep Dive: The Observability Stack (Kube-Prometheus-Stack)The Kube-Prometheus-Stack (KPS) represents a complex integration challenge because it contains multiple distinct web interfaces—Grafana, Prometheus, and Alertmanager—each with different authentication capabilities. While Grafana is a modern application with robust OIDC support, Prometheus and Alertmanager are primarily backend systems with rudimentary UI protections, making them ideal candidates for different Authentik integration strategies.4.1 Grafana: Advanced OIDC Integration with Role MappingGrafana is the visualization crown jewel of the stack. We will utilize its generic_oauth module to integrate with Authentik. The goal here is not just authentication, but authorization mapping: ensuring that users in the Authentik "Admins" group become Grafana Admins.Authentik Configuration:Create a Provider of type "OAuth2/OpenID".Redirect URI: https://grafana.lab.local/login/generic_oauth. This specific path is hardcoded in Grafana's generic OAuth implementation.Scopes: Ensure email, profile, openid, and critically, groups are selected. The groups scope is necessary to pass the user's group memberships in the ID Token.Create an Application named "Grafana" and bind it to this provider.Helm Chart Configuration (values.yaml):We configure Grafana via the grafana.ini block in the KPS values file. The configuration uses JMESPath to perform the logic of role assignment.YAMLgrafana:
grafana.ini:
server:
root_url: https://grafana.lab.local
auth.generic_oauth:
enabled: true
name: Authentik
allow_sign_up: true
client_id: "grafana_client_id_from_authentik"
client_secret: "grafana_client_secret_from_authentik"
scopes: "openid profile email groups"
auth_url: "https://authentik.lab.local/application/o/authorize/"
token_url: "https://authentik.lab.local/application/o/token/"
api_url: "https://authentik.lab.local/application/o/userinfo/" # Role Mapping Logic: # If 'Grafana Admins' is in the user's groups list -> Admin # If 'Grafana Editors' is in the user's groups list -> Editor # Otherwise -> Viewer
role_attribute_path: "contains(groups[*], 'Grafana Admins') && 'Admin' |

| contains(groups[*], 'Grafana Editors') && 'Editor' |
| 'Viewer'"
role_attribute_strict: true
Insight: The role_attribute_path is a powerful feature often overlooked. Without it, all users typically default to "Viewer" or "Editor" depending on the global default, negating the benefits of RBAC. The JMESPath expression contains(groups[*],...) parses the JSON array returned by the Authentik UserInfo endpoint. Debugging this often requires inspecting the Authentik user events to see exactly what JSON payload is being sent.4.2 Prometheus and Alertmanager: Securing the Backend via Forward AuthPrometheus and Alertmanager do not support OIDC. They can be configured with basic auth, but managing static password files in Kubernetes Secrets is cumbersome and lacks MFA support. Deep Dive: The Media Aggregation Stack (*Arr Suite)The *Arr suite (Sonarr, Radarr, Prowlarr) presents a unique challenge: these applications are hybrids. They serve a user-facing GUI that needs protection, but they also expose API endpoints used heavily for inter-application communication (e.g., Prowlarr pushing indexer configurations to Sonarr). A naive Forward Auth implementation would block these API calls, breaking the automation pipeline.5.1 The "Basic Auth" Bridge StrategyTo solve the API/GUI dichotomy, we employ a sophisticated feature of Authentik: Basic Auth Impersonation. The *Arr apps natively support HTTP Basic Authentication. We can configure Authentik to inject these credentials for us.Authentik Configuration:Group Attributes: Create a group called "Media Users". In the group's "Attributes" section, define the credentials that the *Arr apps expect:YAMLsonarr_user: "admin"
sonarr_password: "complex_shared_password"
radarr_user: "admin"
radarr_password: "complex_shared_password"
Proxy Provider: Edit the Proxy Provider used for Sonarr.Enable Set HTTP-Basic Authentication.Username Key: sonarr_userPassword Key: sonarr_passwordApplication Config: In Sonarr/Radarr settings, set the Authentication Method to "Basic (Browser Popup)" or "Forms" (depending on version, but Basic is often more reliable for header injection).The Workflow:
When a user logs into Authentik and accesses Sonarr, Authentik reads the sonarr_user and sonarr_password from their group attributes. It constructs the Authorization: Basic <base64> header and injects it into the request sent to Sonarr. Sonarr sees the valid header and logs the user in immediately, bypassing its own login screen.5.2 Handling Prowlarr and API AutomationProwlarr needs to talk to Sonarr's API. Prowlarr uses an API Key (X-Api-Key header) to authenticate. return request.path.startswith('/api')
Binding: Bind this policy to the Sonarr Application.Effect: Allow.Order: 0 (Highest priority).Unauthenticated: Enabled (This is crucial: it allows the check to pass even if the user is not logged in).This configuration creates a split-horizon security model: The GUI (/) is protected by strong Authentik MFA/SSO, while the API (/api) is exposed but protected by the application's native API Key mechanism. This balances security with functionality.5.3 Ingress ConfigurationThe Ingress annotations for Sonarr, Radarr, and Prowlarr follow the standard Forward Auth pattern defined in section 4.2.YAMLapiVersion: networking.k8s.io/v1

Losing the PostgreSQL database means losing all configurations.Blueprints: Authentik allows exporting configuration as "Blueprints" (YAML). Regularly export your blueprints.
